# 独立 Harness 节点与服务器健康面板 · 第一阶段实施契约

> 状态：设计方案，**尚未实现、验证或部署**。对应控制平面与执行平面分离的第一阶段；不改变原有 8 个一级导航。

## 目标及现状

OtterNest 现有 AgentRuntime 健康自报、任务 DAG、领取/租约/epoch、检查点、审批、CommandPlan、事件和 Runner 能力。不要重复建设第二套任务/授权数据库。现有代码尚未证明真实远端唤醒、进程控制、跨机恢复与外部平台集成可靠性。

目标：OtterNest 控制平面运行在现有主机，独立 Linux Harness 节点运行指挥 Agent 和受限执行 Worker；后台可看到“服务器卡片”、任务执行过程和准确的失败/未知状态。初期只接入一台执行节点，不要求 GPU。

## 部署与信任边界

- **控制平面**：FastAPI + PostgreSQL + Web 控制台，负责权威状态、项目/任务、调度、身份、审批、审计、事件、成果索引；不承载高负载模型推理/构建。
- **Harness 节点**：单台独立 Linux 主机上分别运行 orchestrator 与 runner 容器/服务，按任务隔离 workspace、CPU/内存/进程/运行时间；仅处理明确授权的任务。指挥 Agent 产出任务计划和候选操作，不得直接授予自身权限。
- **通讯**：节点主动通过受控 TLS 通道连接控制平面的最小 Agent API；不对公网暴露 SSH、Docker socket、PostgreSQL 或后台管理端口。凭据按节点独立签发、可撤销/轮换、仅授予最小项目作用域。严禁在日志、前端或任务文本中展示令牌。
- **业务命令**：复用现有 task claim、epoch、TaskGrant、CommandPlan、TaskSideEffect、artifact 与审计。所有操作重验服务端权限；R3/生产部署/合并/破坏性系统操作需人工批准。禁止由 Agent 直接修改核心授权/审计规则。

## 最小数据契约（实施时复用现有模型，先核对现有字段）

服务器视图是 AgentRuntime/节点健康报告的聚合，不能仅凭 TCP 连通声称任务还在执行。建议字段：

| 字段 | 语义 |
|---|---|
| node_id, display_name | 稳定标识与人类可读名称 |
| platform, agent_version | OS/架构、上报组件版本 |
| observed_at, last_heartbeat_at | 数据采样时间与最后一次可信心跳 |
| connectivity | online / stale / offline / unknown（根据阈值计算） |
| cpu_percent, memory_used_bytes, memory_total_bytes | 主机资源采样；无数据时显示未知 |
| disk_used_bytes, disk_total_bytes | 磁盘采样，保留单位 |
| gpu_devices | 可选 GPU 名称、显存、利用率；没有 GPU 为 none，采集失败为 unknown |
| available_capabilities | 已核验可执行能力；声明 ≠ 已验证 |
| running_task_ids | 经权威租约与节点报告对账的任务列表 |
| last_error, report_version | 已脱敏错误与上报协议版本 |

展示时必须区分“节点最后上报在线”“任务已领取”“外部进程确实启动”“任务结果已提交”“结果已验收”；节点失联不等于进程停止。健康数据只做监控，不触发自动授予权限。

## 最小闭环

1. 所有者在「AI 指挥中心」创建任务，选择已核验能力、项目授权和候选节点。
2. 指挥 Agent 提交可审查计划，由控制平面创建/更新任务；有风险操作先经 CommandPlan/TaskGrant 审批。
3. 节点按现有 claim/lease/epoch 协议领取任务，报告启动时间、进度、脱敏日志、检查点、工具调用及外部副作用。
4. Agent 在隔离环境执行；结果和 SHA-256 成果经现有 API 提交，标记 submitted，仍需所有者验收。
5. 失联或超时进入 unknown/reconciliation，不自动假定远端进程已终止；恢复前核对 epoch、外部副作用台账与幂等键，防止重复部署/删除。

## UI 布局（不增加一级菜单）

- 「AI 指挥中心」：任务输入、计划预览、当前执行节点、执行时间线、异常与待审批。
- 「Agent 与接入」：节点注册/停用、连接状态、能力核验、运行实例、凭据轮换入口（不显示令牌）。
- 「系统设置 → 系统状态」：每台远程节点一张紧凑卡片，显示在线状态、最近心跳、CPU/内存/磁盘/GPU（如有）、当前任务数；进入详情再查看环境、服务、日志。
- 节点异常卡片明确标注“最后采样时间”，缺数据则显示“未知”，不展示虚构的百分比或“正常”。

## 分阶段交付与验收

### P0：真实状态卡片与可信节点连接
- 用真实 API/真实采样显示节点状态，禁止生产 UI mock 数据冒充实时状态。
- 节点离线/心跳过期/采样字段缺失的显示准确；节点 token 可撤销。
- 记录 node_id + timestamp + correlation_id 的审计事件；服务端隔离不同项目。
- 用单节点在私有网络验收；断网、重启、错误令牌均测试。

### P1：指挥 Agent → Worker 端到端任务
- 一条经授权的开发/测试任务从后台创建、领取、开始、上传成果、人工验收到结束。
- 运行日志带 correlation_id、task_id、lease_epoch；日志脱敏；进度不是完成证明。
- 验证超时/崩溃/重复投递/租约过期/审批拒绝时不会越权、不会重复执行未对账副作用。
- 控制平面重启后权威任务状态与审计记录保持一致。

### P2：多 Agent 与运维增强
- 有验收证据的 DAG 交接、有限并发、公平调度、预算、失败告警、灰度升级/回滚。
- 至少两台节点跨机恢复演练，备份还原及生产发布门禁；完成安全和负载审计后再考虑公网暴露。

## 明确不包含

首阶段不做自动安装任意模型、完全自主生产部署、直接 SSH root 执行、无需审批的代码合并、对订阅型第三方 Agent 的虚假唤醒承诺，也不声明高可用。

## 首个代码 PR 建议拆分

1. **read-only node status**：AgentRuntime/节点状态聚合 API + 数据契约测试。
2. **node heartbeat collector**：节点签名/鉴权、字段验证、错误脱敏与失联规则测试。
3. **server cards**：在「系统状态」接入上述 API，含空态/离线态/异常态响应式测试。
4. **remote task proof**：单节点端到端开发/测试任务、租约对账与故障演练。

每个 PR 单独执行前后端测试与权限回归，通过后才进入下一步；不直接合并至 main 或部署。
