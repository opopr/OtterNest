# 02 · 系统架构与资源边界

## 三大平面

1. **Interaction Plane**：私人 Web Dashboard、Command Center、任务/记忆/Agent 页面、审批、监控与通知。管理接口仅对所有者开放；远程管理优先考虑私人网络（如 Tailscale）。
2. **Control Plane**：承载轻量模块化单体及 PostgreSQL。负责业务状态、治理、调度、事件、权限、任务与成果索引。
3. **Execution Plane**：Muse 云端环境、支持的 Codex 运行方式、Google AI 工具、其他自有云主机/沙箱。负责模型工作、研究、代码、浏览器、测试。

外部 Agent 未必能够加入私人网络；如果需要远程接入，只暴露**最小受控 HTTPS Agent API**，与私人后台及 PostgreSQL 完全分离。

## 单一业务内核，多协议外观

MCP / A2A / REST / Webhook / SSE 等是不同的入口与事件形式。它们应调用**同一套核心业务命令与授权检查**，不能各自维护另一套任务状态。

建议逻辑内核：

- Identity & Governance（身份、角色、属性权限、审批和审计）
- Project & Goal（项目自治契约、目标、预算和完成条件）
- Task & Execution（依赖 DAG、租约、检查点、恢复、版本）
- Agent Registry & Team（身份、能力验证、团队角色与环境映射）
- Memory & Context（证据、知识发布、按权限上下文组装）
- Event & Workflow（持久事件、订阅、重试和规则）
- Artifact & Decision（版本化成果、决策记录、独立验证）

这些是**逻辑模块**，不必是独立进程或服务。

## 数据与计算分工

- PostgreSQL：事务型状态、JSONB、全文检索、ACL、任务/事件/记忆索引和审计。`pgvector` 仅在资源允许且有明确收益时引入。
- 文件存储：项目原始文件、大型文档、代码包、测试证据、日志附件；PG 保存地址、哈希、元数据、权限及版本。
- 高算力工作（向量生成、复杂文档解析、模型推理、代码编译、浏览器自动化）放在执行平面，不依赖控制平面主机。
- 初期不要求 Redis、Kafka、RabbitMQ、Elasticsearch。若性能/吞吐量客观需要，再评价是否引入。

## 可用性与失败语义

- 核心状态来自数据库权威记录；客户端看到的事件流只是状态更新通道。
- `LISTEN/NOTIFY` 可提示新事件但不作为持久消息系统；事件存储在 PG。
- 服务失联 ≠ 任务已停止；心跳过期 ≠ 外部进程被强制终止。
- “已创建”“已投递”“已接收”“已启动”“已提交”“已验收”必须区分。
- 外部状态可为 **unknown**（未知）并带最近已确认的时间戳。
- 降级模式：仍可查看数据、审批、禁用故障扩展；保护模式暂停危险写入/新调度。

## 可扩展性原则

- 先采用模块化单体，内部模块边界明确。
- 扩展分为受信内置模块与不可信外部扩展；外部扩展通过授权 API，而不是 DB 管理权限。
- 协议、能力与数据分别版本化；旧执行节点可以能力协商或明确拒绝不支持的工作。
- 复杂插件、实验和高级推理不可成为最小可用核心的依赖。

## 基础约束

- 轻量控制平面定位：不在控制平面主机上运行大型语言模型、高负载编译测试或大规模向量检索，不能在单节点前提下虚称高可用保证。
- 控制平面单机存在单点故障；备份、恢复演练和外部任务安全恢复是必要的后续验证项。
