# 31 · 目标生命周期与依赖

## 状态与权限

目标由系统所有者管理，状态为 `active`、`paused` 或 `completed`。所有者可以暂停活动目标、恢复已暂停目标，并在满足完成门槛后提交完成确认。暂停目标会阻止关联任务的新调度和领取，也不能再关联新任务；已运行的远端执行不会被此操作自动终止。已完成目标是终态；如工作范围变化，应新建后续目标，不通过重开旧目标改写历史。

## 完成门槛

- 每个前置目标必须为 `completed`。
- 关联到该目标的每个任务必须通过所有者验收并处于 `completed`；`blocked`、`cancelled`、`submitted` 和其他状态都会阻止目标完成。
- 没有关联任务的目标仍可由所有者按其成功标准人工完成。
- 完成请求必须提供至少 5 个字符的完成依据。依据进入项目事件流，因此有权读取项目事件的成员可以查看；不要在其中填写密钥或其他敏感信息。

完成后目标依赖查询会将该目标报告为已满足。工作流规则可以订阅 `goal.status_changed`，并按 `condition_status` 匹配目标的当前状态。

## API

- `GET /api/v1/projects/{project_id}/goal-board`：读取目标、依赖状态、关联任务进度和当前完成阻塞项。
- `POST /api/v1/projects/{project_id}/goals`：创建目标，字段为 `title`、`success_criteria` 和 `priority`。
- `POST /api/v1/goals/{goal_id}/dependencies`：添加同项目的前置目标，JSON 为 `{"predecessor_id":"..."}`。拒绝跨项目、自依赖、重复边和环。
- `DELETE /api/v1/goals/{goal_id}/dependencies/{predecessor_id}`：移除前置关系。
- `POST /api/v1/goals/{goal_id}/status`：更新目标状态。示例：`{"status":"paused"}`、`{"status":"active"}` 或 `{"status":"completed","note":"所有验收项已完成并核对结果"}`。

改变目标状态和依赖关系需要所有者身份。系统进入 `readonly_protect` 时拒绝这些写操作。目标状态事件记录原状态、目标状态；完成事件还记录完成依据。

## 手工验收清单

1. 在管理台创建目标 A、B，并让 B 依赖 A；目标面板应展示前置状态和任务进度。
2. 尝试完成 B；在 A 未完成时应收到前置目标阻塞提示。
3. 为 A 关联任务并提交；在任务尚未由所有者验收通过时，A 应显示未完成任务数且拒绝完成。
4. 验收完成 A 的所有关联任务，为 A 提交完成依据；A 的状态变为 `completed`，项目事件中包含状态变化。
5. 完成 B；之后暂停、恢复或修改 B 的依赖均应被拒绝。
6. 尝试创建循环依赖和跨项目依赖；两者都应被拒绝。

## 限制

- 系统不会自动判断 `success_criteria` 是否已达成；完成是所有者的明确确认。
- 目标依赖仅在同一项目内建立。跨项目 Portfolio 目前提供公平调度和优先级，不代表跨项目目标依赖。
- 已完成目标没有重开、撤销或重新验收流程。需要改正结果时创建后续目标并保留原目标事件。
- 完成依据写入项目事件并非加密存储，也不会进行敏感信息检测。
